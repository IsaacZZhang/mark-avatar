# 01 · 产品定义与技术选型

## 1. 产品定位

**一句话**：30 秒内给头像加一个有趣的角标，一键换回微信头像。

这类工具型小程序的特征是**高瞬时流量、低留存、强热点驱动**。所以架构上不要追求大而全，而要追求三件事：

| 目标 | 架构含义 |
|------|----------|
| 打开就能用 | 首屏不请求网络也能出水印（内置素材包） |
| 热点能追 | 素材运营不发版上新（CDN 热更） |
| 作品即广告 | 每张导出图自带小程序码角标 |

### 用户路径（MVP）

```
冷启动 → 首页（一张大图 + 素材横滑分类）
       → 点「+」选图：微信头像 / 相册
       → 选水印：素材列表点击即预览
       → 微调：拖拽 / 双指缩放旋转 / 透明度
       → 点「保存头像」→ 导出 1080px → 存相册
       → 结果页：换微信头像引导 + 分享给好友 + 再来一张
```

**关键体验指标**：从打开小程序到图片进相册 ≤ 30 秒，操作步骤 ≤ 4 步。

## 2. MVP 功能边界

我用「必须 / 二期 / 三期」划了三档，避免第一版就摊大饼。

| 功能 | 档位 | 说明 |
|------|------|------|
| 微信头像获取（头像填写能力） | **P0** | 核心入口，必须 |
| 相册/拍照选图 | **P0** | 顺带覆盖非头像场景 |
| 预设素材库（分类浏览 + 点击即用） | **P0** | 首版 30~50 个，覆盖 6~8 个分类 |
| 水印拖拽/缩放/旋转 | **P0** | 不做的话会被评为"太简陋" |
| 导出保存到相册 | **P0** | 核心出口 |
| 素材 CDN 热更 + 分类热榜 | **P1** | 运营能力 |
| 多水印叠加 | **P1** | 组合玩法 |
| 自定义文字水印（字体/颜色/描边） | **P1** | 需 `msgSecCheck` 内容安全 |
| 分享对比卡片 / 小程序码角标 | **P1** | 增长 |
| 激励视频解锁精品包 | **P1** | 变现 |
| 一键更换微信头像引导 | **P1** | 微信不开放 API，只能做引导页 |
| UGC 上传素材 + 审核 | **P2** | 社区飞轮 |
| 视频/动图水印（GIF 头像） | **P2** | 复杂度陡增 |

## 3. 后端方案对比

| 维度 | A. 微信云开发 | B. 纯前端零后端 | C. 自建 Go 后端 |
|------|---------------|-----------------|------------------|
| 上线周期 | **1~2 天接入** | 0 天 | 1~2 周（域名备案另算） |
| 域名备案 | **不需要** | 不需要 | **需要**（国内服务器 + ICP 备案） |
| 素材热更 | ✅ 云存储 + CDN | ❌ 必须发版 | ✅ |
| 数据统计/排行 | ✅ 云数据库 | ❌ | ✅ |
| 内容安全 `msgSecCheck` | ✅ 云调用免鉴权 | ❌ 不能做 | ✅ 需自管 access_token |
| 小程序码生成 | ✅ 云调用免鉴权 | ❌ | ✅ 需自管 |
| 运维成本 | 几乎为 0 | 0 | 需人管 |
| 成本（日活 1 万量级） | 几十元/月 | 0 | 服务器固定成本 |
| 可控性 | 中 | 低 | **高** |
| 你现有 Go 栈复用 | ❌ 云函数是 Node | - | ✅ |

**结论：选 A。** 云开发的价值不在"能写后端代码"，而在于**免鉴权云调用**（小程序码、内容安全这两个接口自建要管 access_token 很烦）和**免备案**。你的 Go 栈在这里用不上，也没必要用上——这个小程序的服务端逻辑薄到只有 5 个云函数。

> 如果你后续确实要做 AI 生成水印（服务端出图），那时候再接自建 Go 后端做混合也不迟，架构上留了口子（见 03 文档的接口设计）。

## 4. 渲染方案对比

水印合成有两条路，选错会返工。

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **端侧 Canvas 2D** | 实时预览、零服务端成本、离线可用、支持手势编辑 | 受设备性能影响、需处理 dpr 适配 | ✅ **选定** |
| 服务端合成（云函数 + sharp/ImageMagick） | 效果一致、可做复杂滤镜 | 每次预览都要往返网络，交互卡顿；云函数冷启动 + 出图成本高 | ❌ 仅作为 AI 玩法备选 |
| CSS + `wx.canvasToTempFilePath` 截屏 | 开发快 | 无法精确控制导出尺寸，真机字体渲染差异大 | ❌ |

**Canvas 2D 的三个硬约束**（踩过就知道）：

1. `type="2d"` 模式**没有 `ctx.draw()` 和 draw 回调**，导出前不需要等回调，但也意味着绘制必须同步完成
2. 图片必须用 **`canvas.createImage()`** 创建，不能用 `new Image()`；`src` 必须是本地路径或已在 `downloadFile` 合法域名内的地址
3. 画布 buffer 默认按**逻辑像素**创建，3x 屏会发虚 —— 必须手动 `canvas.width = w * dpr` 并 `ctx.scale(dpr, dpr)`

## 5. 技术选型汇总

| 层 | 选型 | 理由 |
|----|------|------|
| 渲染 | 原生小程序 + Canvas 2D | 只有一个核心页面，不上 Taro/uni-app 反而更快，也少一层兼容问题 |
| UI 组件 | **不引第三方组件库**，自写轻组件 | TDesign 全量引入会撑大主包；本小程序 UI 极简 |
| 状态 | `app.globalData` + 页面 data | 状态就一个「当前编辑会话」，不需要 MobX |
| 后端 | 微信云开发（Node 18 云函数） | 见上 |
| 素材存储 | 云存储 + 自带 CDN | 天然在白名单内，免配置 |
| 统计 | 云数据库 + 自定义埋点 | 不引第三方 SDK，省包体 |
